## Parallel JPEG encoding and HTTPS uploads - 14 November 2026

- A new 40.02-second physical-camera baseline on the sequential JPEG firmware observed 90 distinct images at production, 2.219 fps across receipt timestamps, median JPEG size 15,492 bytes, median server frame age 0.228 seconds, and median authenticated image retrieval time 2.95 ms. - Firmware now overlaps encoding on the Arduino core with a dedicated upload task on core 0. Exactly three bounded packet slots represent encoding, uploading, and at most one latest waiting frame. Critical sections exchange only ownership; payload encoding and network I/O happen outside locks. Each encoder callback receives its own packet context. Published waiting frames replace older waiting frames; a sending packet is not reused until its HTTP response has been consumed. Transport clients have one owning task. The reconnect-discard flag is atomic. In PSRAM pipeline mode a producer-owned raw scratch buffer is copied before returning the driver buffer, so the camera can refill while JPEG encoding proceeds; sequential fallback avoids that extra allocation.

The single RGB565 driver buffer, 320 x 240 resolution, quality 88, and 4:4:4 chroma remain configured. Without PSRAM or if the sender task cannot be allocated, the code selects sequential uploads.
